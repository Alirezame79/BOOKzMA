# راهنمای وایب‌کدینگ BOOKzMA

این راهنما برای مالک پروژه است. قانون‌های الزام‌آور عامل در `AGENTS.md` هستند؛ این فایل توضیح می‌دهد چطور با AI کار کنی و خروجی‌اش را خودت کنترل کنی.

## ۱. نقشهٔ فایل‌ها

| فایل | مخاطب | کاربرد |
| --- | --- | --- |
| `AGENTS.md` | عامل‌های کدنویسی | قوانین canonical، دستورها و محدودیت‌ها |
| `CLAUDE.md`، `.github/copilot-instructions.md` | ابزارها | اشاره‌گر کوتاه به AGENTS؛ محل کپی قانون‌ها نیست |
| `.github/skills/` | عامل‌ها | روال‌های تکرارشونده برای قابلیت، migration، مستندات، انتشار و ارزیابی بیرونی |
| `ARCHITECTURE.md`، `BOT_GUIDE.md` | عامل و توسعه‌دهنده | واقعیت تأییدشدهٔ معماری و رابط فعلی |
| `docs/DECISIONS.md`، `docs/ROADMAP.md` | مالک و عامل | تصمیم‌های فنی و ایده‌های آینده |
| `docs/LOCAL_DEV.md`، `docs/TESTING.md` | توسعه‌دهنده | اجرای محلی و روش تست |
| `docs/SECURITY_PRACTICES.md`، `docs/PERFORMANCE.md`، `docs/BACKUP.md` | توسعه‌دهنده | قواعد امنیت، عملکرد و طراحی پشتیبان‌گیری |
| `docs/specs/TEMPLATE.md` | مالک و عامل | تعریف رفتار و معیار پذیرش پیش از کد |
| `docs/vibe/` | مالک | آموزش و promptهای آماده |

مستند کوتاه و دقیق بهتر از متن طولانی و کلی است. برای هر واقعیت یک خانهٔ canonical نگه دار و از بقیه لینک بده.

## ۲. حلقهٔ کار هر تغییر

1. نیاز را با spec در `docs/specs/` روشن کن.
2. از P-02 برنامه بخواه: فایل‌ها، خطرها، گزینه‌ها و تست‌ها.
3. طرح را بخوان و موارد نیازمند تأیید را صریحاً تأیید کن.
4. پیاده‌سازی را با P-03 بخواه و روی branch کاری جدا انجام بده.
5. diff، تست‌ها، مستندات و رفتار ربات تست را خودت بررسی کن.
6. تغییر مستندات و ROADMAP را با کد تطبیق بده.
7. merge و deploy را دستی و با توجه به backup/migration انجام بده؛ عامل اجازهٔ خودکار push یا deploy ندارد.

## ۳. چه وقت فقط برنامه، چه وقت پیاده‌سازی؟

| برنامه بگیر و قبل از کد تأیید کن | معمولاً مستقیم قابل انجام است |
| --- | --- |
| قابلیت جدید یا تغییر API/کلاینت | اصلاح متن فارسی در `texts.py` |
| جدول یا migration | باگ کوچک با علت روشن و بدون تغییر قرارداد |
| Docker، env، entrypoint یا dependency | تست برای کد موجود |
| تغییر معنای استریک یا یادآور | refactor بدون تغییر رفتار/public API |
| امنیت، عضویت، مجوز، حذف داده، پیام گروهی | اصلاح مستندات و غلط املایی |
| ارزیابی/انتقال پروژهٔ خارجی | |
| وقتی خودت هنوز دقیق نمی‌دانی مسئله چیست | |

قاعده: اگر برگشت تغییر دشوار یا اثرش روی کاربر زیاد است، اول برنامه. تغییر migration، استریک، امنیت یا انتشار نیازمند تأیید مالک است.

## ۴. نوشتن prompt خوب

هدف و دلیل را بگو؛ فایل/لایهٔ مرتبط را نام ببر؛ محدوده و چیزهایی که نباید تغییر کنند را روشن کن؛ شکل خروجی را مشخص کن؛ هر prompt را روی یک کار متمرکز نگه دار. اگر مبهم است از عامل بخواه حداکثر سه سؤال بپرسد. از او بخواه دستورهای اجراشده و خروجی واقعی را گزارش کند. هیچ‌وقت token، رمز، DSN، فایل `.env` یا دادهٔ واقعی کاربر را در prompt نگذار.

## ۵. بررسی خروجی AI

- `git diff` را بخوان و هر فایل را با هدف کار تطبیق بده.
- ببین تست جدید واقعاً رفتار را می‌سنجد؛ تست حذف یا ضعیف‌شده را نپذیر.
- `noqa`، `type: ignore`، dependency و API جدید را بررسی کن.
- خودت `ruff check . && pytest` را اجرا کن و خلاصهٔ واقعی مثل `N passed` را ببین؛ خروجی ادعایی عامل کافی نیست.
- تغییرات را برای واژه‌های `token`, `password`, `secret`, `.env` از نظر نشتی بررسی کن، اما مقدار secret را در چت چاپ نکن.
- `git status --short` را ببین تا فایل محلی مثل `dev_run.py` یا backup وارد کار نشده باشد.
- رفتار را با ربات تست و حالت خطا بررسی کن. برای migration، فایل را بخوان و روی دیتابیس خالی آزمایشی امتحان کن.
- مستندات را با کد مقایسه کن. بپرس: «این را کجا اجرا کردی؟ دستور دقیق و خروجی واقعی چه بود؟»

## ۶. جلوگیری از تغییر خطرناک

روی branch جدا کار کن و تغییرات کوچک را بازبینی کن. قبل از اجرای عملیات بیرونی یا حذف داده تأیید بگیر. مجوز دائمی برای `rm`، `docker compose down -v` یا `git push --force` نده. عامل را به سرور، `.env` یا دیتابیس اصلی وصل نکن. پیش از migration سرور، backup بگیر و بازیابی‌پذیری آن را بررسی کن.

`git restore` می‌تواند تغییرات محلی را دور بریزد. فقط بعد از بررسی status و diff و فقط برای فایل‌هایی که مطمئنی متعلق به همان کار هستند اجرا کن؛ هرگز برای پاک‌کردن تغییر ناشناخته استفاده نکن.

## ۷. محلی و production

Production با Compose اجرا می‌شود: PostgreSQL و Uvicorn که API، long polling ربات و scheduler را در یک process بالا می‌آورد. مالک گزارش می‌کند که محلی فقط DB را با Compose اجرا می‌کند و ربات تست را با `dev_run.py` و تنظیم proxy خودش بالا می‌آورد. این فایل عمداً gitignored است و نباید خوانده یا تغییر داده شود؛ جزئیات implementation آن بررسی نشده.

جملهٔ استاندارد برای prompt: **«با اجرای Docker در production و با اجرای محلی `dev_run.py` سازگار بمان؛ این فایل محلی را باز یا تغییر نده و اگر سازگاری را نمی‌توانی تأیید کنی، آن را صریح گزارش کن.»**

## ۱۰. وقتی عامل گیر کرد یا خراب کرد

اول کار را متوقف کن و `git status` و `git diff` را ببین. خطای کامل و دستور دقیق را بده. اگر لازم است برگردانی، فقط فایل‌های تغییرکردهٔ همین کار را پس از بازبینی مشخص کن؛ تغییرات محلی ناشناخته را restore نکن. برای جلوگیری از تکرار خطای روند، قانون پایدار را در `AGENTS.md` اصلاح کن؛ همان قانون را در چند فایل کپی نکن. درس موردی را در spec یا DECISIONS ثبت کن.

## ۱۱. Skills

Skill یک دستورکار کوتاه برای کار تکرارشونده است. در `.github/skills/<name>/SKILL.md` از frontmatter با `name` و `description` استفاده می‌شود. skill جدید را فقط وقتی بساز که روال تکرار می‌شود و قواعدش از `AGENTS.md` کپی نشده، بلکه مراحل خاص کار را تعریف می‌کند.

## ۱۲. یادداشت‌های مخصوص BOOKzMA

- FastAPI از قبل هست: `api.py` routeها و auth را پیاده کرده و Docker با Uvicorn آن را در کنار ربات اجرا می‌کند. «افزودن FastAPI» واقعیت نیست؛ گسترش بیشتر API نیازمند کلاینت/نیاز واقعی و spec است.
- ربات محلی مالک از توکن تست جدا و proxy محلی استفاده می‌کند؛ جزئیات فایل `dev_run.py` بررسی نشده. هرگز توکن production را هم‌زمان در دو poller اجرا نکن.
- طراحی فعلی single-instance است: polling، FSM پیش‌فرض حافظه‌ای، scheduler و کش عضویت per-process هستند.
- یادآورها هر ۳۰ ثانیه کل جدول را بررسی می‌کنند و برای هر candidate ممکن است queryهای اضافی بزنند. قبل از بهینه‌سازی، اثر واقعی را اندازه بگیر.
- CI فعلی وجود دارد. اما تست محلی در این محیط به‌خاطر وابستگی `httpx2` در `TestClient` هنگام جمع‌آوری متوقف شد؛ این نتیجه را با pass اشتباه نگیر.
- docs قبل از این کار با کد تناقض داشتند؛ همیشه `api.py`, `Dockerfile`, `bot.py`, migrations و config فعلی را مرجع بگیر.
